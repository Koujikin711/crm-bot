# Анализ нестыковок и возможных проблем в main.py (CRM-бот)

## 1. Критичные / логические ошибки

### 1.1 Статистика медицины (📈 Статистика лидов) — период не применяется к «Продано» и «Дозвон»
**Где:** `med_stats_cb` (около строк 1892–1901).

- **Пришло** (`all_l`) считается с фильтром по периоду: `last_touch >= start_str OR payment_date >= start_str[:10]`.
- **Обработано (дозвон)** (`ans_l`) и **Продано** (`sold_l`) считаются **за всё время** (без фильтра по периоду).

В итоге в одном сообщении смешаны «за период» и «за всё время», проценты (c_ans, c_sale) считаются от разнородных баз и вводят в заблуждение.

**Рекомендация:** добавить для медицины фильтр по периоду и для `ans_l`, и для `sold_l` (аналогично бизнес-статистике: по `last_touch` и/или `payment_date` в выбранном периоде).

---

### 1.2 Лимиты записей к врачам не работают
**Где:** `DOCTOR_LIMITS` (строка 486), `can_add_appointment`, `med_load` (1870–1872).

- В коде везде используются ключи `'assistant'` и `'ganchina'` (нижний регистр).
- В `DOCTOR_LIMITS` задано только `{"Ганчина": 10}` (с большой буквы).

В результате `DOCTOR_LIMITS.get('assistant', 0)` и `DOCTOR_LIMITS.get('ganchina', 0)` дают 0 — лимиты не применяются, в «Нагруженность» показывается «g_cnt/5», хотя лимит для Ганчины по коду фактически 0.

**Рекомендация:** привести ключи к одному виду, например:
`DOCTOR_LIMITS = {"assistant": 10, "ganchina": 5}` и использовать те же строки при записи в `appointments` и в сообщении «Нагруженность».

## 2. Дублирование и мёртвый код

### 2.1 Два обработчика для одной кнопки «📂 Загрузка данных»
**Где:** первый — около 1665, второй — около 2027.

Оба хендлера на `F.text == "📂 Загрузка данных"` делают одно и то же: выгрузка лидов бизнеса в Excel. В aiogram срабатывает последний зарегистрированный, первый по сути не используется.

**Рекомендация:** оставить один обработчик «📂 Загрузка данных» (бизнес), второй удалить, чтобы не путаться при правках.

## 3. Риски по данным и граничные случаи

### 3.1 Длина `callback_data` (лимит Telegram 64 байта)
**Где:** кнопки с `re_{phone}_{uid}`, `cl_{phone}`, `rp_{phone}` и т.п.

- В части мест `phone` обрезается до 30 символов (`phone[:30]`), в других — нет (например, в `try_assign_queued_lead_to_manager` и в части `cl_`/`rp_` передаётся полный `phone`).
- Для `re_{phone}_{uid}` используется `[:64]` по всей строке — при длинном номере может обрезаться `uid`, и переназначение уйдёт не тому менеджеру.

**Рекомендация:** везде, где в `callback_data` попадает номер, использовать `phone[:30]` (или единую константу), а для `re_` — формировать `re_{phone[:30]}_{uid}` без обрезки по 64 символам так, чтобы `uid` не обрезался.

---

### 3.2 Auth_queue: старые записи с `instance_sphere = NULL`
**Где:** создание лида из второго сообщения (около 649): `(q[1] or 'biz') == instance_name`.

Если номер уже есть в `auth_queue` с `step=1` и `instance_sphere = NULL` (старая запись), то при втором сообщении в **медицину** условие даёт `'biz' == 'med'` → False, лид не создаётся.

**Рекомендация:** для совместимости со старыми данными можно использовать `(q[1] or instance_name) == instance_name`: при неизвестной сфере считать, что второй контакт пришёл в текущий инстанс.

---

### 3.3 Лид в очереди (pending): сессия в chat_sessions не чистится
**Где:** при переводе лида в pending (менеджер неактивен или в диалоге с другим клиентом), строки 561–564, 567–570.

Обновляются `leads` (manager_id=NULL, status='pending'), но запись в `chat_sessions` для этого менеджера и этого номера не удаляется. Для сценария «менеджер был в чате с A, пришло сообщение от B → B в очередь» это не критично, но при смене статуса менеджера старые сессии могут оставаться в БД.

**Рекомендация:** при переводе лида в pending при необходимости вызывать `DELETE FROM chat_sessions WHERE user_id = ? AND phone = ?` для этого менеджера и номера.

## 4. Потенциальные проблемы

### 4.1 Два разных FSM-состояния для ввода суммы в медицине
**Где:** `Form.med_payment_sum` (админ: «💰 Оплаты» — ввод суммы) и `Form.med_paid_sum` (менеджер: «💰 Оплатил» → выбор пакета → сумма).

Имена похожи, но состояния разные, обработчики разные — конфликта нет. Имеет смысл не путать их при дальнейших правках (например, не объединять в одно состояние без разделения сценариев).

---

### 4.2 «Лиды в работе»: владелец без выбранного меню
**Где:** `wl` (около 1770): `sphere = data.get("owner_current_sphere")`.

Если владелец не нажимал «🏥 МЕДИЦИНА» или «💼 БИЗНЕС», то `sphere` будет None, и условие `is_owner(...) and sphere == "med"` не выполнится — всегда покажется список по бизнесу. Это ожидаемое поведение (нужно сначала выбрать раздел), но можно в интерфейсе подсказать: «Сначала выберите 🏥 Медицина или 💼 Бизнес».

---

### 4.3 Менеджер бизнеса: нет кнопки «Поступления лидов»
В меню владельца/админа бизнеса есть «📥 Поступления лидов», у менеджера бизнеса такого пункта нет — доступ к воронке только у админа/владельца. Если по задаче менеджерам не нужен доступ — всё ок; иначе нужно добавить пункт и проверку прав.

---

## 5. Безопасность и конфигурация

### 5.1 Токены и ключи в коде
**Где:** строки 24–31: дефолтные значения `API_TOKEN`, `ID_INSTANCE`, `API_TOKEN_INSTANCE` и т.д. в коде.

Если `.env` не подставлен или не используется в проде, токены попадут в репозиторий. Лучше в проде не задавать дефолты для секретов и читать только из окружения (или падать при их отсутствии).

## Приоритет исправлений

1. **Высокий:** лимиты врачей (`DOCTOR_LIMITS`), статистика медицины по периоду (ans_l, sold_l).
2. **Средний:** один обработчик «📂 Загрузка данных», единообразное ограничение длины `callback_data` для phone, при желании — очистка `chat_sessions` при переводе в pending.
3. **Низкий:** auth_queue при `instance_sphere = NULL`, подсказка владельцу по «Лиды в работе», проверка доступа к «Поступления лидов» для менеджеров.
