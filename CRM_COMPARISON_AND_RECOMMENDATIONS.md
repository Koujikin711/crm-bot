## Как работают типичные CRM (аналоги)

- **Воронка/этапы:** этапы типа «Новый → В работе → Договор → Оплата → Закрыт» с движением по шагам.
- **Теги/метки:** теги по лиду (источник, продукт, срочность) и фильтрация по ним.
- **Автоматизация:** авто-назначение по правилам (round-robin, по тегу), авто-смена этапа по действию/времени.
- **Аналитика:** воронки по периодам, конверсия по этапам, среднее время в этапе, прогноз.
- **Задачи/напоминания:** «перезвонить через N часов», задачи по лиду с дедлайном.
- **Командная работа:** комментарии к лиду, внутренние заметки, история изменений (кто что сделал).
- **Безопасность:** роли и права на действия, аудит, секреты только из окружения.

У вас часть этого уже есть (очередь, назначение, отказ с комментарием, напоминания), но без явных «этапов воронки», тегов и задач по лиду.

## Минусы именно в вашем коде

### 1. Архитектура и поддержка

- **Всё в одном файле** (~2500 строк). Хендлеры, БД, бизнес-логика и работа с WA в одном месте — сложно тестировать и менять по частям.
- **Нет слоя доступа к данным:** запросы к БД разбросаны по хендлерам, дублируются условия (`direction = 'med'`, `direction = 'biz' OR direction IS NULL`). При смене схемы правки по всему файлу.
- **Синхронный `execute_query`:** блокирует event loop на время SQLite. При росте нагрузки лучше вынести в thread/process или перейти на async SQLite.

### 2. Безопасность

- **Токены и ключи в коде по умолчанию** (строки 24–31). Если забыть .env — утечка в репозиторий. В проде лучше не задавать дефолты и падать при отсутствии переменных.
- **Нет проверки прав на действие с лидом:** например, любой, кто знает callback, теоретически может дергать кнопки. Имеет смысл проверять, что лид принадлежит сфере/менеджеру текущего пользователя перед сменой статуса/перенаправлением.

### 3. Надёжность и граничные случаи

- **Нет retry при сбоях Green API:** при временной ошибке запрос теряется. Для критичных действий (отправка в WA, создание лида) полезен повтор с экспоненциальной задержкой.
- **Жёсткая привязка к одному номеру в leads (phone PRIMARY KEY):** один человек с двумя номерами = два лида, объединить нельзя. В аналогах часто есть «контакт» с несколькими телефонами.
- **Один и тот же номер не может быть и в biz, и в med:** при смене направления старый лид игнорируется (логика «lead_dir != instance_name»). Это осознанное ограничение, но оно неочевидно для пользователя.

### 4. UX и полнота данных

- **Нет явных этапов воронки:** статусы есть (active, chatting, thinking, closed), но нет настраиваемых «стадий сделки» и отчётов по переходам между ними.
- **Нет тегов/меток у лида:** нельзя пометить «горячий», «повторный», «из рекламы» и фильтровать списки/отчёты.
- **История изменений лида ограничена:** есть lead_events (incoming/outgoing/status_change/manager_change), но нет «кто и когда изменил поле X» в одном месте для аудита.

### 5. Уже отмеченные в ANALYSIS_INCONSISTENCIES.md

- Лимиты врачей и период в статистике медицины уже правились ранее; дубли «📂 Загрузка данных» и риски по callback_data/chat_sessions тоже разбирались. Если что-то из этого вернулось после правок — стоит свериться с тем файлом.

## Функции, которые стоит добавить (по приоритету)

### Высокий приоритет

1. **Задачи по лиду**  
   «Перезвонить через 2 часа», «Написать завтра» с напоминанием в боте. Таблица `tasks (lead_phone, user_id, text, due_at, done)` и фоновый job, который шлёт уведомление менеджеру.

2. **Внутренние заметки к лиду**  
   Поле или таблица `notes (lead_phone, user_id, text, created_at)`. В карточке лида — кнопка «Заметка» и вывод последних 3–5 записей. Чтобы несколько менеджеров могли оставлять комментарии без смены статуса.

3. **Источник лида (тег/метка)**  
   Поле `source` у лида (например: «сайт», «WhatsApp», «реклама») и фильтр в отчётах/списках. Опционально — теги в отдельной таблице (many-to-many), если понадобится несколько меток на лид.

### Средний приоритет

4. **Воронка с этапами (для бизнеса)**  
   Отдельная таблица этапов (например: новый → звонок → встреча → предложение → оплата) и поле `stage_id` у лида. Статистика: сколько лидов на каждом этапе, конверсия между этапами за период.

5. **Отчёт «Время в работе»**  
   По лидам с `created_at` и датой закрытия считать среднее время от создания до закрытия (по сфере/менеджеру). Помогает оценивать скорость обработки.

6. **Экспорт с фильтрами**  
   Выгрузка в Excel не только «все лиды бизнеса», но и по периоду, статусу, менеджеру, сфере (медицина отдельно), чтобы строить отчёты вне бота.

### Низкий приоритет

7. **Разделение кода на модули**  
   Вынести в отдельные файлы: `db.py` (execute_query, init_db, все запросы к БД), `wa.py` (Green API), `handlers/` (owner, biz, med, leads, dialogs), `keyboards.py`. В main — только инициализация и запуск. Так проще искать баги и добавлять функции.

8. **Конфигурируемые тексты**  
   Приветствия и шаблоны сообщений в БД (таблица `settings` или `messages`) или в конфиге, чтобы менять тексты без правок кода.

9. **Базовый аудит**  
   Таблица `audit_log (user_id, action, entity_type, entity_id, old_value, new_value, created_at)` для критичных действий (смена статуса, перенаправление, отказ, оплата). Потом можно смотреть «кто что сделал» по лиду.
